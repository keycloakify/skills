# i18n (translations)

All of this applies to the **login theme** and the **Multi-Page account theme**. For the account theme, replace `keycloakify/login` with `keycloakify/account` and `src/login/` with `src/account/`. The Single-Page account theme and the email theme work differently (see the end of this file).

## How it works

- Keycloakify ships the default Keycloak messages for 30 languages: ar, ca, cs, da, de, el, en, es, fa, fi, fr, hu, it, ja, ka, lt, lv, nl, no, pl, pt-BR, pt, ru, sk, sv, th, tr, uk, zh-CN, zh-TW.
- The defaults live in `node_modules/keycloakify/src/login/i18n/messages_defaultSet/`. Never edit them there. Override them instead (see below).
- The active language comes from Keycloak. Enable languages per realm under Realm Settings → Localization (Internationalization on, supported locales, default locale).
- **Choose the language from the app**, not with the theme's dropdown. Pass `ui_locales=fr` on the authorization request: oidc-spa, keycloak-js and NextAuth all support it. The dropdown still works as a fallback.
- All configuration lives in one file, `src/login/i18n.ts`. It exports `useI18n` and `type I18n`.

## Using messages in components

```tsx
const { msg, msgStr, advancedMsg, advancedMsgStr } = i18n;

<h1>{msg("loginAccountTitle")}</h1>                    // JSX (<span data-kc-msg="...">), renders embedded HTML
<input placeholder={msgStr("username")} />             // plain string – use for attributes, document.title, etc.
<label>{advancedMsg(attribute.displayName ?? "")}</label> // key or "${key}" not known at compile time
```

- `msg` / `msgStr` only accept known keys: the defaults plus your custom keys. TypeScript rejects anything else.
- Use `advancedMsg` / `advancedMsgStr` for keys that are defined on the server, such as User Profile display names (`${profile.attributes.favourite_pet}`), `termsText`, or labels coming from `kcContext`.
- Svelte: `const { msg, msgStr, advancedMsg } = $i18n;` then `{@render msg("backToLogin")()}`.
- Angular: `[innerHTML]="i18n.msgStr('backToLogin') | kcSanitize: 'html'"`.
- Some default messages contain HTML. `msg()` renders it sanitized. If you inject `msgStr()` output as HTML yourself, wrap it with `kcSanitize`.

## Override default messages or add new keys

Find the key by inspecting the rendered HTML: `msg()` output carries `data-kc-msg="<key>"`. You can also search `messages_defaultSet/en.ts`.

```ts
// src/login/i18n.ts
import { i18nBuilder } from "keycloakify/login";
import type { ThemeName } from "../kc.gen";

const { useI18n, ofTypeI18n } = i18nBuilder
  .withThemeName<ThemeName>()
  .withCustomTranslations({
    // WARNING: must be inline literals – no imports, spreads from other files, or computed values
    en: {
      loginAccountTitle: "Log in to your ACME account", // override a default
      myCustomMessage: "Need help? Contact support."    // new key → msg("myCustomMessage") type-checks
    },
    fr: {
      loginAccountTitle: "Connectez-vous à votre compte ACME",
      myCustomMessage: "Besoin d'aide ? Contactez le support."
    }
  })
  .build();

type I18n = typeof ofTypeI18n;
export { useI18n, type I18n };
```

- **Why inline only:** Keycloakify analyzes this file at build time and injects the messages into the generated `.ftl` files, so server-side error and feedback messages can use them too. Messages imported from JSON or another module are silently ignored.
- Add every new key to `en` at least. Languages you don't provide fall back to English.

## Add a language Keycloak doesn't ship

1. Create a file with **all** default keys translated, for example `src/login/i18n.hi.ts`:

```ts
import type { MessageKey_defaultSet } from "keycloakify/login";

const messages: Record<MessageKey_defaultSet, string> = {
  doLogIn: "साइन इन करें",
  doRegister: "रजिस्टर करें",
  // ... every key from node_modules/keycloakify/src/login/i18n/messages_defaultSet/en.ts
};

export default messages;
```

   - Start from `en.ts`. An LLM translation is fine as a first pass.
   - Don't put product-specific wording here. Use `withCustomTranslations` for that.

2. Register it in `i18n.ts`. `getMessages` is a dynamic import, so the file is loaded lazily:

```ts
const { useI18n, ofTypeI18n } = i18nBuilder
  .withThemeName<ThemeName>()
  .withExtraLanguages({
    hi: {
      label: "हिन्दी",                       // shown in the language dropdown
      getMessages: () => import("./i18n.hi")
    }
  })
  .withCustomTranslations({
    en: { /* ... */ },
    hi: { loginAccountTitle: "अपने ACME खाते में साइन इन करें" } // custom keys for the new language too
  })
  .build();
```

3. Enable the locale in the realm's Localization settings.

Builder order: `withThemeName` → `withExtraLanguages` → `withCustomTranslations` → `build`.

## Per-theme-variant wording

When `themeName` is an array in `vite.config.ts` (for example `["acme-1", "acme-2"]`), a message can take an object keyed by theme name instead of a string:

```ts
.withCustomTranslations({
  en: {
    doLogIn: "Log in!",                       // same for all variants
    loginAccountTitle: {
      "acme-1": "Log in to your ACME1 account",
      "acme-2": "Log in to your ACME2 account"
    }
  },
  fr: {
    doLogIn: "Se connecter !",
    loginAccountTitle: {
      "acme-1": "Connectez-vous à votre compte ACME1",
      "acme-2": "Connectez-vous à votre compte ACME2"
    }
  }
})
```

## Messages defined in the Keycloak realm

- Realm-level messages work out of the box for some keys:
  - `termsText`
  - User Profile attribute display names, helper texts and select option labels (`profile.attributes.<name>`, and so on)

  Render them with `advancedMsg`.
- **Not every realm override reaches the theme.** If a realm Localization override of a default key (for example `doRegister`) is ignored, force it through `kcContextExclusionsFtl` in `vite.config.ts`:

```ts
keycloakify({
  kcContextExclusionsFtl: `
    <@addToXKeycloakifyMessagesIfMessageKey str="doRegister" />
    <@addToXKeycloakifyMessagesIfMessageKey str="invalidUserMessage" />
  `
})
```

  To debug what got injected, check `dist_keycloak/theme/<themeName>/login/login.ftl`.
- Rule of thumb:
  - Wording that belongs to the theme goes in code (`withCustomTranslations`).
  - Wording that admins must change without a rebuild goes in the realm, and you may need `kcContextExclusionsFtl`.

## Previewing languages

Storybook, one story per language:

```tsx
export const French: Story = {
  render: () => <KcPageStory kcContext={{ locale: { currentLanguageTag: "fr" } }} />
};
```

- To change the default for every story, set `overrides: { locale: { currentLanguageTag: "de" } }` in `createGetKcContextMock(...)` in `src/login/KcPageStory.tsx`.
- In the dev server: `getKcContextMock({ pageId: "login.ftl", overrides: { locale: { currentLanguageTag: "es" } } })`.
- In real Keycloak: run `npx keycloakify start-keycloak`, enable the locales in `myrealm`, then use the dropdown or `?ui_locales=fr`.

## Language selector in an ejected Template

- The template reads `currentLanguage` and `enabledLanguages` from `i18n`. Each language has a `label` and an `href`, and following the `href` switches the locale.
- In v10 this was `currentLanguageTag`. See troubleshooting.md for the migration.
- Set `<html lang>` and `dir` yourself if you need them. For RTL languages such as `ar` and `fa`, set `dir="rtl"`. This is not handled automatically and isn't covered in the docs.

## Single-Page account theme and email theme

- **Single-Page account:**
  - The translation files carry instructions at the top. Create an **override** file and don't own the base translation file.
  - You can't use `i18nBuilder` here.
- **Email (native):** messages are Java `.properties` bundles under `src/email/messages/` (for example `messages_en.properties`), used from the FreeMarker templates with `${msg("key")}`. Add one file per locale. Check the layout `initialize-email-theme` generated, because this isn't detailed in the docs.
- **Email (keycloakify-emails / jsx-email):** follow that library's README for i18n.

Docs: https://docs.keycloakify.dev/features/i18n
